For an interactive coding session, choose a launcher and run it from your
project:

```sh
routekit codex
routekit claude
```

The native client opens in the current directory with a suitable startup model.
Use its model picker to switch among compatible RouteKit routes. Pass an exact
`provider/model` only when a script, reproducible run, or one-off comparison
must control the startup model.

RouteKit's TypeScript packages are not tested or supported as a public embedded
API. Applications should use the CLI-managed daemon and authenticated HTTP
gateway. See [TypeScript API status](/docs/reference/api) for the boundary.

## Update or remove RouteKit

Most RouteKit work follows the same five-stage loop:

1. **Configure** a provider or enroll a subscription account.
2. **Verify** live discovery with `routekit providers status` and
   `routekit models list`.
3. **Connect** a coding tool or authenticated HTTP client.
4. **Observe** health, usage, and call attribution.
5. **Diagnose** with `routekit doctor` and daemon logs when a route stops
   behaving as expected.

Use the [command reference](/docs/reference/commands) when you already know the
task and only need exact syntax.

## Before shared or production use

- Review [router configuration](/docs/reference/configuration) for provider,
  model, authentication, and network settings.
- Read [privacy and stored data](/docs/concepts/privacy).
- Use an exact build listed in [supported coding tool versions](/docs/reference/client-compatibility).
- Keep the default loopback bind unless an authenticated network boundary is
  intentional.
- Use named data-plane tokens instead of sharing the private owner token.
